# Design decisions

Gaps in `alang-specs.md` that the implementation had to close. Each is decided by the six principles; the rule
numbers refer to the spec. Open points are listed at the end.

## Lexical

| Topic          | Decision                                                                                                                                                                                                            | Principle                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Comments       | None. `//`, `/*` and `#` get a dedicated diagnostic pointing to `doc`.                                                                                                                                              | 3.7: text is printed from the tree, a free comment would be lost.    |
| String escapes | Exactly `\"`, `\\`, `\n`, `\t`, and `\u{X}` (uppercase hex) for other control characters. Every other character, including non-ASCII, is written as itself; `\u{41}` is rejected. Raw control characters are rejected. An unknown escape is E0005; the C escapes `\r`, `\0`, `\a`, `\b`, `\f`, `\v` and `\e` get their `\u{...}` form as `expected` and `fix` (`\u{D}`, `\u{0}`, `\u{7}`, `\u{8}`, `\u{C}`, `\u{B}`, `\u{1B}`), except `\0` before a digit, a C octal escape (`\033`) that `\u{0}` would misread. Other unknown escapes get no fix, and no escape is added. The card names one of them, `\r` as `\u{D}`: in the tasks round (2026-11-14) E0005 for `\r` in an example string was the only language diagnostic, and it cost a resend of 21 definitions. The other C escapes stay with E0005's fix, which keeps the card at its length. | 3: every string has exactly one spelling.                            |
| Strings        | Double quotes only, closed on the same line.                                                                                                                                                                        | 3                                                                    |
| Numbers        | 4.7 is enforced both ways: `65535` and `1_000` are errors, as are leading zeros. Floats are `digits.digits`, never in exponent form; the printer expands `1e-7` to `0.0000001`. `-0` is rejected.                                                                                  | 3, 4.7                                                               |
| Negative       | `-3` is a literal. There is no unary minus on other expressions; write `0 - x`.                                                                                                                                     | 3: one form.                                                         |
| Keywords       | Section names (`doc`, `in`, `out`, `effects`, `requires`, `ensures`, `examples`, `body`, `record`, `variant`, `where`) are reserved, so `out: Unit` can never be read as a parameter. **Language change (2026-11-14, E4):** `target` is a section word only in an `extern fn` and is not reserved: it stands after `examples`, where an entry is a call (`name(`), so the token after it (`:`) decides, as for `with effects` in std signatures. Reserving it would break `examples/lines.alang` (a local `target`), the tickets round's `fn tickets.target` and every program with such a name; const's C1 hit the same wall with `value`. Alternatives: reserve `target`; the section `extern:` (no new word, but departs from the spec's own word). | 1: no lookahead needed.                                              |
| Foreign forms  | `===`, `!==`, `&&`, `\|\|`, `!`, `{`, `}`, `?`, `;`, `'`, `var`, `null`, `while`, `import`, ... have dedicated diagnostics (E0006). Since list literals, `[` and `]` are symbols; index access (`xs[0]`) and the list type `Int[]` get E0006 from the parser, which sees them as `[` right after an expression or a type (2026-11-13, L4). Since map literals (2026-11-13, M8), the message for `{` and `}` ends with "and a map is written `[key: value]`", and the one for index access names `std.map.get(map: m, key: k)` beside `std.list.get`. Since shared cases (2026-11-14, T9), `\|` is E0006 too, after `\|\|` ("`\|` does not exist; patterns that share an arm are joined with `or` (`case A or B then`), and logic is `or`."), quoting the whole line, with `expected` `or` and as fix the line with every `\|` outside its strings, and the spaces around it, replaced by ` or ` (`outsideStrings` in `lexer.ts`). Constants (2026-11-14, C12): `MAX_ITEMS`, a word of capitals, digits and at least one underscore, is E0002 "Constants and other values are written in snake_case: `max_items` (3.6)." with the lower-case word as fix (it used to suggest `MAXITEMS`); `Max_Items` keeps the PascalCase fix. `const` in a body is E0006 with `let` as its fix. Around generic headers (2026-11-14, 5.7): a bound (`<T: Ord>`, `<T extends Ord>`, `<T: Eq + Show>`) is E0006 "A type parameter takes no bounds: alang has no traits (2.6). Take what the function needs of `T` as a parameter, such as `same: (T, T) -> Bool` or `by: (T, T) -> Order`.", without a fix; `end fn util.last<T>` is E0103 "The block end names the definition without its type parameters: `end fn util.last`." with the end line as fix, as for a wrong name; `case Leaf<Int> then` is E0101 "A pattern takes no type arguments; the `match` subject gives them: `case Leaf then`."; `const m.c<T>` is E0101 "A constant has one type and takes no type parameters; a value for every type is a `fn` with a type parameter, such as `fn m.empty<T>`." (G11). `import` (2026-11-14, P7) is E0006 "There are no imports; write names from other modules fully qualified. Code from a TypeScript module is called through an `extern fn` with `target: \"./module.ts#name\"`.", naming the extern. | 5.7, 4.6                                                             |

## Syntax

| Topic                | Decision                                                                                                                                                                                                         | Principle                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Line breaks          | Required between statements and section entries. Inside `( )` of calls, applications and constructs, and inside `[ ]` of a list or a map, they are ignored. Indentation never matters.                                               | 3.7                                           |
| Parentheses          | Not stored in the tree. The printer emits exactly those that 3.5 requires (and `a - (b - c)` on the right of the same group). `(a) + b` prints as `a + b`.                                                       | 3.7                                           |
| Lambdas as operands  | Always parenthesized, since a lambda body extends as far right as possible: `(fn(x: Int): Int => x) == f`.                                                                                                     | 3.7                                           |
| `not`                | Binds looser than comparison: `not a == b` is `not (a == b)`.                                                                                                                                                    | 3.5                                           |
| `a.b.c`              | Parsed as a neutral dotted name; whether it is a local with fields, a constant with fields, or a definition by its full name is resolved later (Type checking, Names). A dotted path followed by `(` is a call (or, with unnamed arguments, an application: Applying a function value); if its first segment is a local whose field chain does not lead to a function value, it is a method call and reported (E0220). | 3.1, 1.2                                      |
| `f<T>(...)` vs `a < b` | After a path, `<` starts type arguments only if a type list closed by `>` and followed by `(` parses; otherwise it is a comparison. After the name of a case or record, `<` starts type arguments if a type list closed by `>` parses (G7, 2026-11-14): a construction has no order (E0211) and comparisons do not chain (E0102), so only text that was an error before reads differently; `n < Limit` and `n < (limit)` stay comparisons.                                                                             | 1.4                                           |
| Function types       | **Language change (2026-11-14, F1, F5, F6).** `(A, B) -> R`: the parameter types in parentheses, at least one, then `->` and the result type, the notation std, `showType`, `search_type` and E0204 already printed. It stands wherever a type does (`in`, `out`, fields, case values, `let`, `let [...]`, `for`, lambdas, type arguments: `List<(Int) -> Bool>`, `std.list.empty<(Int) -> Bool>()`), nests to the right (`(Int) -> (Int) -> Int` gives a function, and a function parameter stands in the parentheses, `((Int) -> Int) -> Int`), and stays on one line, as `<...>` does. `->` is a lexer symbol; no other text has `-` right before `>`. The printer needs no parentheses beyond the parameter list. A function type names no parameters: a lambda's own names would contradict them, and one type would get many spellings (3.7). Without parameters it is E0101 "A function type takes at least one parameter: a pure function without parameters always gives the same value, so take that value instead (`limit: Int`)." (F5); a function with `in: none` passed by name keeps the internal type `() -> T`, which has no written form. `with effects` after a function type is E0101 (F3; Effects, Function values). Foreign forms (5.7) are E0006, without a fix: `(x: Int) -> Int` "A function type names no parameters: `(Int) -> Int`; the names belong to a lambda, `fn(x: Int): Int => ...`.", `(Int) => Int` "A function type is written with `->`: `(Int) -> Int`; `=>` starts the body of a lambda.", `Int -> Int` and `(Int) -> Int -> Int` "A function type puts its parameter types in parentheses: `(Int) -> Int`.", `fn(Int) -> Int` and `fn(Int): Int` "A function type is written `(Int) -> Int`, without `fn`; `fn(x: Int): Int => ...` is a lambda, which is a value." After `<`, where the parser backtracks to read a comparison when no type list parses, these errors are passed on, since no expression can hold these forms there: `std.list.empty<(x: Int) -> Int>()` gets the message about names, while `n < (limit)` still reads as a comparison. The `fn` form is not passed on, since a lambda may follow `<`. Alternatives: named parameters `(left: T, right: T) -> Order`; the generic E0101 "Expected ..." for the foreign forms. | 1.1, 1.3, 3, 3.7, 5.7 |
| Applying a function value | **Language change (2026-11-14, F2).** `by(a, b)`, `rule.broken(line)`: a path followed by `(` and unnamed arguments, at least one, applies a function value by position, since a function type names no parameters, as a case's value has none (4.2). A path followed by `(` and named arguments, or by `()`, always calls a function defined with `fn`, so the two never collide and a local may still share a function's name. The first argument decides, by the two tokens `name :` after `(` (line breaks skipped), as `payload()` tells `Port(value: 1)` from `Some(x)`. Line breaks inside the parentheses are ignored and the arguments print on one line with `, `; as an operand the application is an atom (`not test(high)`, `rule.broken(line).name`). Parser errors: a later argument written `name: value` is E0107 "A function value takes its arguments by position, without names: `by(a, b)`; a function defined with `fn` takes every argument by name." (in a named call, a later unnamed argument keeps "Every argument carries its parameter name: `name: value`."), and a comma before `)` is E0101 "An argument list ends after its last argument; remove the comma before `)`." An example may have an application on the left (`twice(2) == 4`), so that the checker names the parameters (E0107). Not available: applying a call's result (`make(n: 1)(2)`); bind it first (4.5). Alternatives: named application through names in the type (needs named function type parameters); application only through std. | 4.1, 4.2, 1.2, 1.1 |
| Variant case names   | A case's full name is `module.Case`, so case names are unique per module across types. Written short inside the module.                                                                                          | 1.2: one name, one meaning.                   |
| `if` without `else`  | Only as a statement; an `if` that yields a value (after `let ... =`, `return`, or inside an expression) needs `else` (E0110).                                                                                   | 3.4                                           |
| Propagation statement | **Language change (2026-11-14, T1, T2).** `expression else return value` is a statement: a `Result<Unit, E>` or `Option<Unit>` is propagated without a binding, `error` as in a let-else (`std.fs.write_text(path: p, text: t) else return Err(error)`). It is the let-else without the name, as a `Unit` call is a `let` without the name, so the five dummy names of the rounds (`let written: Unit = ...`) disappear. The expression is not an `if`, `match` or `for` (those keep E0101 "Expected a line break, found `else`."), and an `else` on the line of the `then` that opened the enclosing `then` branch belongs to that `if`: the parser passes the `then` line to the block, so `if c then f(x: 1) else return v end if` keeps its meaning as an `if` with an `else` branch. A non-canonical `if` whose `else` ends a `then`-branch line (`if c then` / `f(x: 1) else return v` / `end if`) now reads as a propagate and gets E0224, never a silent change. Printed `<expression> else return <value>`. Alternatives: a leading keyword (`check f() else ...`); `let _: Unit`, which needs `_`; a greedy `else` like `let`'s, which would change an accepted one-line `if`. | 3, 3.7, 2.6, 1.1 |
| Taking a list apart  | **Language change (2026-11-14, T11, T12).** `let [a, b]: List<T> = expression else return value` binds the items of a list that has exactly as many items as names, in order; any other length returns the `else` value, in which `error` is `Unit`. Every round program took a list apart by position with a length check and `std.list.get` (ledger, wordcount, logstat, tasks, `lines.alang`); names in order replace counting indices (4), as named arguments do. Names only, at least one, no `_`, no literals, no nesting, no rest name; `else return` is required, since the length can always differ. Line breaks inside the brackets are ignored, and the names print on one line with `, `. Parser errors (E0101): "A `let [...]` names at least one item.", "A `let [...]` ends after its last name; remove the comma before `]`.", "A `let [...]` takes a list apart into names only: ..." and "A `let [...]` needs `else return ...` for a list of another length."; `result` and `error` are E0109 as for any binding. No list patterns in `case` (E0101 naming `let [...]`, `std.list.first` and `std.list.drop`): without a catch-all (3.3) no set of list patterns covers every length, and literal items could never be exhaustive. Alternatives: `[a, ...rest]` patterns with length exhaustiveness; at least as many items, not exactly. | 3.2, 3.3, 4 |
| Shared cases         | **Language change (2026-11-14, T6, T9).** `case P or Q then`: cases handled alike share an arm. Each alternative is a whole pattern, only at the top of a case, printed on one line with ` or ` between them. The keyword `or` already means alternation in alang, and C# uses `or` for patterns; a comma inside parentheses would read as a second value (4.2), and nested alternatives would give a second form. A case line is one entry (3.7), from `case` to `then`: a line break after or before `or` is E0101 "A `case` and all its patterns stand on one line, up to `then`." A name alternative is still E0108. Foreign forms (5.7): `case A \| B` is E0006 (Lexical); `case A, B then` (Go, Java, Kotlin, Swift) is E0101 "Patterns that share an arm are joined with `or`: `case A or B then`." with the case line's commas turned into ` or ` as fix (none if the line holds a `"`); `case Err(A or B) then` is E0101 "`or` joins whole patterns of a case, not the values inside one: ..." without a fix. Evidence is thin (the ledger round's three arms with one body each rebuilt the error they matched); the `tickets` round tests it. Alternatives: `case P, Q`; `P \| Q`; nested alternatives. | 3, 3.3, 3.7, 4.2, 5.7 |
| List literal         | **Language change (2026-11-13, L1, L2, L5, L6).** `[a, b, c]`, with at least one item: the empty list keeps its one spelling `std.list.empty<T>()`, which 1.4 names, and `[]` is E0228 (Type checking). Printed on one line with `, ` between items; line breaks inside the brackets are ignored on input; a trailing comma is an error (E0101: "A list ends after its last item; remove the comma before `]`."). The form most languages and `std.text.show` use, so examples can state lists. An append chain stays legal: rule 3 concerns forms of the grammar, not values that are equal. Alternatives: `List(1, 2, 3)`, which looks like a case with several values (4.2); a trailing comma allowed and dropped in print. | 3, 3.7, 5.1                                   |
| Map literal          | **Language change (2026-11-13, M2, M3).** `["a": 1, "b": 2]`, with at least one entry: every entry is `key: value` (no space before the colon, one after it), entries are separated by `, ` and printed on one line, line breaks inside the brackets are ignored on input, around `:` too, and there is no trailing comma. The first entry decides list or map: after `[` and the first expression, a `:` makes the literal a map (1.1, left to right). `[:]` parses only so that E0228 can name `std.map.empty<K, V>()` and prints as `[:]`. Parser errors (E0101): "A map ends after its last entry; remove the comma before `]`.", "Every entry of a map is `key: value`." and, for a list item followed by `:`, "A list holds items without `:`; in a map, every entry is `key: value`, the first one too." Two equal literal keys are E0234 (Type checking); computed keys that turn out equal trap (kind `key`), and so does `std.map.from_list` with two items of one key: one duplicate rule for every way to build a map, consistent with `zip` (S9). So examples can state maps (5.1), and braces stay foreign (4.4, 5.7). Alternatives: `{"a": 1}`, the model's habit from Python and JSON; the later entry winning, as in most languages. | 1.1, 3, 3.7, 5, 5.1, 5.7 |
| Block value          | The value of a block is its last statement if that is an expression, otherwise `Unit`.                                                                                                                           | 3.4                                           |
| `const`              | **Language change (2026-11-14, C1, C3).** `const shop.max_items` with the sections `doc`, `out` and `body`, in this order and all present, then `end const shop.max_items`. The body is statements ending in a literal `return`, as in a function, so a table can be built with `let`, `if`, `match`, `for` and calls of pure functions. The name is a snake_case value path with a module, as for `fn`; `result` and `error` name no constant (E0109), since the language's own binding would hide it in `ensures` and after `let ... else`. No new reserved word: `doc`, `out`, `body` and `const` were reserved already; `value` could not be, since it names fields everywhere. Alternatives: one expression under a new keyword (`is:`); the one-line `const a.b: T = v`, which has no doc. Habits (C12): the one-line `const shop.max_items: Int = 100` (TypeScript, Rust, Go) is E0101 naming the sections, with the full form as `expected` (`doc: "..."`, the value after `return`; no fix, since the doc is missing); `in:` in a constant is E0101 "a value that takes parameters is a `fn`"; `effects:`, `requires:`, `ensures:` or `examples:` after `out` is E0101 "it is pure and needs no examples"; a PascalCase name (`const shop.MaxItems`) is E0002 with the snake_case fix. | 1.1, 3, 1.3 |
| Generic definitions  | **Language change (2026-11-14, G1, G3).** A function takes type parameters after its name, `fn util.last<T>`, `fn util.pair_up<A, B>`: the form every std hit already printed (`fn std.list.last<T>(...)`), mirrored by the call form `std.list.empty<Int>()`. The end line names the definition without them (`end fn util.last`). A type parameter is one capital letter, `A` to `Z`, written once (E0215): one form, the one std shows, which collides neither with a builtin name (never one letter) nor with TypeScript's global generic names, so the emitter writes it unchanged. The printer writes `<T, U>` only where there are type parameters, so no other text and no hash changes. Parser messages (E0101): `<>` "A definition's type parameters are capital letters in `<...>`: `fn util.last<T>`; without any, write the name alone.", a token that is no single capital letter (`<Item>`, `<t>`, `<1>`) "A type parameter is one capital letter, such as `T` or `K` (3); `Item` is not one.", `<T,>` "A list of type parameters ends after its last letter; remove the comma before `>`."; a missing `>` keeps the generic "Expected `>`, found ..."; the habits around the header are in Lexical, Foreign forms. A type takes them the same way (G8): `type tree.Tree<T>`, `end type tree.Tree`. Alternatives: a `types:` section (a new reserved word, and a section with no `none` form); any PascalCase name (`Item`), mangled in TypeScript. | 1.1, 3 |
| Case type arguments  | **Language change (2026-11-14, G7).** A construction may name its type's arguments after the case or record name, before its value: `None<Int>`, `Ok<Int, String>(1)`, the form of a call's type arguments. The printer writes them as written; `refs.ts` rebuilds them, so `None<net.port.Port>` refers to `net.port.Port`. Where they are needed, allowed or an error is a matter of type checking (`Ok`, `Err`, `None`). A pattern takes none (`case Leaf then`): the `match` subject gives them. | 1.4, 3 |
| `extern fn`          | **Language change (2026-11-14, E1, E4, E7).** A function whose code is TypeScript has the sections of a `fn`, in its order, with `target: "./text.ts#encode"` in place of `body:` and its statements, then `end extern fn text.encode`: the form the spec's Overview names ("with `target` instead of `body`"), so an extern gets a contract and examples for free (5.1, 5.2). `target` holds one string, the module and the name it exports (E3, Type checking). It is a `FnDef` with `target` (and an empty `body`), not a fourth kind, so it is declared, called, searched and stored as a `fn` (E13). No type parameters (E7). Parser messages (E0101 unless stated): `extern type`, `extern const` "Only a function is written in TypeScript: `extern fn module.name`." (P1); `extern fn m.f<T>` "An `extern fn` takes no type parameters: its result is checked against one concrete type where it returns (2.5). Write one extern per type, or keep the generic part in alang." (P2, as G11 for a constant); `body:` in an extern "An `extern fn` has `target: \"./module.ts#name\"` in place of `body:`; its code is TypeScript in that module." (P3); `target:` in a `fn` "A `fn` has `body:`. A function whose code is TypeScript is an `extern fn`, with `target:` in place of `body:`." (P4); a `target` without a string "`target` holds one string: `\"./module.ts#name\"`." (P5); `end fn m.f` closing `extern fn m.f`, or the reverse, E0103 "The block end names `fn m.f`, but the definition is `extern fn m.f`." with the end line as fix (P6). The last message of a definition's start is "Expected a definition (`fn`, `type`, `const` or `extern fn`), found …". E0199 has no use left. Alternatives: inline TypeScript in a string (alang strings are one line with four escapes, so real code becomes one escaped line, and a module-level `import` is impossible). | 1.1, 5.1, 2.5 |
| Definition names     | Always have a module: `fn main` is rejected, `fn hello.main` is required.                                                                                                                                        | 6.2                                           |

## Semantics and runtime

| Topic                | Decision                                                                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `let ... else`       | In the `else` branch `error` is the `Err` value; for `None` it is `Unit`.                                                                      |
| `result`, `error`    | Bound by the language (in `ensures` and in `let ... else`), so they cannot name a parameter or binding (E0109). Fields may use them.          |
| `std.int.parse`      | `String -> Option<Int>`: an optional `-` and the digits `0` to `9`, inside the `Int` range. Unlike in an alang literal (4.7), leading zeros are allowed (`"007"` is 7, `"-0"` is 0) and `_` is not; nor are `+` and whitespace. |
| `Int` division       | `/` truncates toward zero, `%` has the sign of the dividend (`-7 % 2 == -1`), division by zero traps.                                          |
| `Int` zero           | **Language change (2026-11-13, S1).** An `Int` is never `-0`: the runtime turns the `-0` that JavaScript gives (`0 * -1`, `Math.trunc(-1 / 2)`, `Number("-0")`, `Math.floor(-0.0)`) into `0` in every Int operation and every std function that returns an Int. So `x == y` means the same value everywhere, also through `1.0 / std.int.to_float(value: x)` (3.9). A `Float` keeps IEEE `-0.0`. Alternative: leave it and document it. |
| `Float` arithmetic   | IEEE 754; a NaN result traps (`0.0 / 0.0`), infinities are ordinary values (`1.0 / 0.0`).                                                      |
| String order         | By Unicode scalar values, not UTF-16 code units. `std.string.length` counts scalar values.                                                     |
| Representation in TS | `Int`/`Float` → `number`, `Unit` → `null`, records → plain readonly objects with a checking constructor, which registers the object with its type's short name in a `WeakMap` of the runtime (`$rt.record`) for `std.text.show`, leaving the object, its fields and `==` untouched (the runtime registers the std records it builds itself), constants → getters, `export const m$c: () => T = $rt.constant("m.c", (): T => { ... })`, which evaluate the body once, on first use (pure, so synchronous; a use is a call of the getter, then the fields), listed in `$constants` after `$examples` for acceptance (C13; nothing runs at load, so no definition order is needed, and a cycle traps `cycle` instead of reading an unset binding), variants → `{ tag, value? }`, `List<T>` → `ReadonlyArray<T>` (not `readonly T[]`: `readonly readonly number[][]` is not TypeScript). A list literal is emitted as `([a, b] satisfies ReadonlyArray<T> as ReadonlyArray<T>)` with its checked item type, since TypeScript would infer `Some<number>[]` for `[Some(1)]` and then reject an appended `None`. `Map<K, V>` → `$rt.SortedMap<K, V>`, a persistent AVL tree in key order (M4); a map literal is emitted as `$rt.map_literal<K, V>([[k1, v1], [k2, v2]], "<definition>")` with its checked types, whose entries run from left to right, each key before its value, and which traps on a key that occurs twice. A statement without a value (`let`, a propagation statement, `let [...]`) at the end of a value block delivers `Unit` into the block's target, a `return` included, so a `return match` in a `Unit` function whose arm ends in a `let` returns in every branch (it used to fail `deno check`). A propagation statement is emitted as a let-else without the binding. `let [a, b]: List<T> = xs else return v` is emitted as a length test on a fresh constant, then one `const` per name indexed from 0 (`$r1[0]` is `T` in TypeScript, since `noUncheckedIndexedAccess` is off). A `let` whose value is an `if`, `match` or `for` is assigned through a temporary (`let $v1: T;`, the branches assign it, then `const name: T = $v1;`), since a pattern or `let` inside the value may bind the same name, which the `let` makes visible only after it (2.6); assigned directly, the inner TypeScript constant took the assignment and the example crashed (found 2026-11-14 in phase `statements`). A shared case (T10) is one `else if` branch per pattern, each with its own binds and its own copy of the body (fresh temporaries each), so TypeScript narrows each branch as for single cases; the price is output size, which only the TypeScript sees. The alternative, `if (a \|\| b)` with conditional binds, would not narrow. ## Examples and acceptance

| Topic                | Decision                                                                                                                                                                                                                                                      | Principle |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| Acceptance           | One pipeline (6.3): parse, type and effect check, mandatory examples, then run the examples. `alang check`, `ts`, `build` and `run` go through it and refuse a program that fails any step; `fmt` and `test` do not.                                          | 5, 6.3    |
| Missing examples     | A function with `effects: none` and `examples: none` is rejected (E0401), located at `examples: none`. `expected` shows the form of an example from the signature (`twice(n: Int) == Int`); there is no fix, since no tool can invent the expected value. | Runaway recursion    | A stack overflow while running an example is a trap of kind `stack` (E0403), not a crash of the tool. Recursion is the only way to repeat (3), so a missing base case is a common mistake.                                                                    | 3, 5      |

| Equality             | An example holds if both sides are equal under `==`, i.e. structurally (3.9). The left side runs first.                                                                                                                                                       | 3.9       |

| Constants            | **Language change (2026-11-14, C4).** A constant is evaluated once, lazily, by a getter; acceptance evaluates every constant, in definition order, before the examples run, from one load of the built module. A trap there is E0404 (`section` `body`, `at` `const <name>`), reported at the constant the trap came from, so a constant that traps only because one it uses does gets nothing; a constant that needs its own value, directly or through the constants and functions it uses, traps `cycle` ("The constant loop.a depends on itself: loop.a -> loop.b -> loop.a."), reported once per cycle. The examples still run, so unrelated failures come in the same round; one whose trap came from a constant is not reported when there are E0404s (5.6). No static cycle check: every path that runs a program accepts it first (`check`, `ts`, `build`, `run`, `db run`), and a constant has no inputs and is pure, so acceptance meets exactly the cycles a run would meet, with no false ones, and an accepted program never traps `cycle`. A static check would need the call graph through every function a constant calls and would reject a reference on a branch the evaluation never takes; a cheap one of direct constant-to-constant cycles would report the same cause twice. Alternative: eager evaluation in dependency order, which needs the same graph. Risk: a constant first used deep in a recursion is evaluated there. | 5, 6.3, 5.6 |
| Where examples run   | In the tool's process, on the generated TypeScript (spec, Toolchain), for a program without an `extern fn`; one with an extern runs them in a separate process (next row). | — |
| Foreign code at acceptance | (2026-11-14, E10, E11.) A program with at least one `extern fn` evaluates its constants and runs its examples in a separate Deno process, in every path that loads the built module (`accept` and so `check`, `ts`, `build`, `run`, every submit and `alang db run`; `alang test`): `testProgram` decides, and `load` never imports such a program into the tool. The process gets no `--allow-*` flag at all, `--no-config` (a project `deno.json` changes nothing), `--no-lock`, `--no-remote` and `--cached-only` (a remote import is refused before any fetch, a package comes only from Deno's cache), `--quiet` and `NO_COLOR`; stdin is closed and stdout piped, so it never writes to the MCP channel. Everything else on stdout is ignored. Values cross as tagged JSON (`{ "$float": "-0" \| "Infinity" \| "-Infinity" }`, `{ "$map": [[k, v], …] }`), and the parent checks the report's shape and counts before using it: it comes from foreign code. Alternatives: a `Worker` with `deno: { permissions: "none" }` (needs `--unstable-worker-options`); every program in a separate process (would break every MCP registration without `--allow-run`). | 5, 6.3 |

## Database

| Topic | Decision | Principle |
| --- | --- | --- |
| Hash | sha-256 of the canonical text (the printer's output, never the submitted text), hex, first 16 characters. Storing a version whose hash exists with a different text is an internal error (collision). The same text always gets the same hash, so a revert, or a remove followed by an add, reuses the earlier version. | 3.7, 6.1 |
| References stay names | **Departs from 6.1.** Stored text refers to other definitions by name, as written; there is no internal hash link. The `text` column holds canonical text and rows never change, and that text contains the definition's own name, so no design that stores it can make `rename` change only a pointer. The guard (6.7) needs a hash that changes exactly when the text a query returned changes; with hash links, a callee's change would re-hash every transitive caller and stale their guards although their text did not change. Consequence: `rename` rewrites every caller, and each caller gets a new version (built later). Recorded alternative: hash-linked storage as in Unison, which needs cycles hashed jointly and stored text that is not the canonical text. | 6.1, 6.7 |
| Tables | As in the spec, except: `names.hash` is unique (a text contains its name, so one version belongs to one name); `refs(from_hash, to_name)` holds names, not hashes, so that `callers(B)` still lists A after only B's body was replaced; `history(id, name, hash, changed_at, operation, other_name)` with `hash` null for a removal and `id` giving the order (one transaction shares a timestamp). `refs` and `signature` are derived from the text. | 6.1, 6.6 |
| `refs` rows | Every full name a version refers to, in order of first use (std names and the definition itself included). A variant case is stored by its own full name (`net.port.OutOfRange`), not its type's, so the rows depend on the text alone and never go stale; `callers` of a type also looks up the users of its cases. | 6.5 |
| Transactions | `submit(changes)`, a change being `add(text)`, `replace(name, hash, text)`, `remove(name, hash)` or `rename(name, hash, to)`, optionally with a text (Rename checks). Each text is parsed on its own and is exactly one definition (E0504); a replaced text keeps the name (E0505; the name also fixes the kind); a name is changed at most once per transaction (E0508). The whole resulting program is then accepted (6.3), which re-runs every example, so a caller whose example a changed body breaks is reported. Either everything is written, in one SQLite transaction, or nothing. | 6.3, 6.4 |
| Which text failed | Every diagnostic of a submit names its definition where it can. The parser names the definition once it has read the header, but the lexer reads the whole text first, so a lexer error (or one in the header) had `definition: null`; in a transaction of 21 adds (the tasks round, 2026-11-14, E0005 for `\r` in an example string) the model had to search all 21 texts. Now such a diagnostic gets the change's `name` (replace, rename; for a rename with text, the old name, as its other diagnostics give it), and for an add the name in the text's first line if it reads `fn <name>` or `type <name>` (read without the lexer, which may be what failed); otherwise it stays null. A name the parser set is kept. | 5.5, 6.4 |
| Guard | `replace` and `remove` with a hash that is not current are rejected (E0501) with the current version in the result's `current` and a fix to the current hash. `add` of an existing name is rejected (E0503), also with the current version. An unknown name (E0502) gets a closest-name fix. Diagnostics of database operations quote the operation as `at`, e.g. `replace(net.port.parse, 1a2b...)`. | 6.7, 5.5 |
| Interface rule | "If `replace` changes the signature, it is rejected and names the affected callers" leaves out the two sections that concern only the definition itself: `doc` and `examples`, so adding an example does not force every caller into the transaction. Everything else counts: for a fn `in` (names, types, order), `out`, `requires`, `ensures` and added effects; for a type its shape (record or variant, fields, cases with payloads, in order) and `where`. Contracts count although acceptance re-runs every example, because callers with effects have no examples (5.4): a tightened `requires` would otherwise surface only as a trap at runtime. Contracts are compared as printed (no proof of implication yet, 5.2); types by full name, and a type parameter, of a function or of a type, by its position (2026-11-14, G13): renaming `<T>` to `<E>` throughout is no interface change, since callers never write the letter, while adding, removing or reordering one is, since every letter occurs in `in` or `out` (E0250). A contract that names a letter (`fn(x: T): Bool => ...`, `std.list.empty<T>()`) is still compared as printed, so such a rename changes it; normalizing letters inside contracts is left for later. The baseline is the current version as the transaction's renames rewrite it, so adapting a definition to a type renamed in the same transaction is no interface change. A change with callers outside the transaction is rejected (E0506), listing them; submitting them unchanged in the same transaction is enough. | 6, 6.4, 5.4 |
| Added effects | Removing an effect is compatible, since over-declared effects are allowed (Effects). An added effect lists every caller that would have to declare it, transitively: the walk stops at callers that declare it already and at members of the transaction. One round shows the whole chain, instead of one layer per attempt. | 2.1, 5.6 |
| Remove | Rejected while callers outside the transaction exist (E0507). Recursion and a function's own examples do not count, nor callers removed in the same transaction. Removing the last definition leaves an empty, accepted program. | 6 |
| Rename | `rename(name, hash, to)` rewrites the renamed definition under its new name and every definition that refers to it (followers), written from its own module: short inside, qualified elsewhere. All renames of a transaction go through one mapping; a variant type that changes module takes its cases along (`net.port.NotANumber` becomes `net.errors.NotANumber`), since case names belong to the module. A caller whose text does not change is not rewritten. History: the new name gets `rename` (other name: the old one), the old name a `rename` entry without hash, each follower `follow`; `history` of the new name continues with the old name's entries. | 6.1 (departs), 1.2 |
| Rename checks | The new name must be free (E0503), differ from the old one, lie outside `std`, and survive printing and parsing as a name of the definition's kind (E0509); both names count toward "one change per name" (E0508). To rename and edit a definition in one transaction, `rename` takes an optional text, `rename(name, hash, to, text)`: the changed definition under its new name (E0505 otherwise), guarded by the one hash. It is written, not rewritten: it counts as a member of the transaction for the interface and remove rules, its own references are not compared for capture (E0510), and its interface is compared with its mechanically renamed form, so callers that the text's interface change affects join the transaction as with `replace`. Followers and renamed definitions are outside the transaction for the interface and remove rules, since they are rewritten, not adapted; a `replace` of a follower in the same transaction wins over the rewrite. | 6.4, 6.7 |
| Rename capture | A rename must not change what a reference denotes. A new name can be captured by a local binding: a function value `by: cmp` renamed to `g` reads a local `g`, and a module renamed to `path` turns `path.parse(...)` into a method call on a parameter `path`, and a type renamed to `m.T` turns `X` into the type parameter `T` inside `fn m.keep<T>` (2026-11-14, G14; the message names type parameters beside local bindings). | Command line | `alang db [--dir <dir>] <command>`: every query and operation, one JSON value on stdout (all but `run`, below), exit code 1 for a rejected operation (diagnostics in the result) or an unknown name (diagnostics on stderr), exit code 2 for a command line it does not understand (also `--` with a command other than `run`). `submit <file>` takes a JSON array of changes, so a transaction of several changes (6.4) is possible from the shell. | Run | `alang db [--dir <dir>] run [<main>] [-- <args>...]` (`Codebase.run`) syncs, accepts the whole current program (6.3), writes it to `out/<main>.ts` with its entry `out/<main>.run.ts` (both stay and are overwritten by the next run, like those of `alang run`), and starts `main` in its own process with exactly the permissions of its effects. Acceptance re-runs every example although every stored state was accepted, so `db run` and `alang run` share one pipeline and a checker newer than the database is noticed. A codebase of many modules can hold several `main` functions: the full name chooses one, and without it there must be exactly one (E0304, listing them). An unknown name is E0502 with a closest-name fix; a definition not named `main` is E0304, since a program starts at a function named `main` (1). A failed sync refuses the run instead of falling back to the database as queries do: an export file that does not parse or check is what the user meant to run, and with E0513 the files contradict the database; either way a run has effects. Stdout belongs to the program; diagnostics go to stderr as JSON with exit code 1; otherwise the program's exit code is passed through (70 for a trap). The program runs in the caller's directory, not the codebase's, like `alang run`. The words after `--` go to the program unchanged (`RunOptions.args`, as in `alang run`). | Toolchain, 6.3 |
| Own-module names | Chosen by the user (2026-11-12) after the playground. Submit and import store an own-module name written in full short instead of rejecting it (E0226), since the stored text, and so the hash, is the same either way: like layout, the full spelling does not survive printing. Applied in the syntax tree, to exactly the places the checker reported, and only when every diagnostic of the program's check is such a name in a definition sent with the change; with any other complaint everything is reported as before, so each diagnostic quotes the text as sent (5.5). The shortened program is checked again; if that fails, the E0226 are reported. A successful result lists the applied diagnostics under `fixed` (absent when empty), so the caller knows where the stored text differs from its own. A rejection after shortening (an example, an interface change) lists them first, since its quotes are of the short text. Other mechanical fixes (effect order E0111, type arguments E0209) are still rejected. | 1.2, 3.7, 5.5 |
| `Unit` bindings fixed | Submit and import also apply E0235's fix themselves (T5, 2026-11-14): a `let name: Unit = ` whose name is unused is dropped, leaving the propagation statement or the expression statement, and the diagnostic is listed under `fixed`, as for own-module names (same rules: only in definitions sent with the change, only when every diagnostic is one of the two, and only if the fixed program checks). A parse error names its file in the message, since it names no definition. | Storage, 6.6 |
| Sync | The export in Git is the source of truth, so the database follows it without a manual step. Table `export_files` holds per module the hash of what its file held when the codebase last wrote or read it (R). `sync` compares, per module, the file (F), what the database would write (D) and R: F = D is in step; F = R ≠ D means the database is ahead (an export write failed after a commit), so the file is written; D = R ≠ F means the file changed (pull, checkout, edit), so the export is imported; all three different is refused (E0513, at `export/<module>.alang`, pointing to `import`, which keeps the database's versions in history, or `export --force`). Files the database is ahead on are written before the import; files left non-canonical by it are rewritten after, so a sync ends with every file as the database would write it. A missing export directory has not been written yet; it is not read as every file deleted. A database without records (from before them) records the files that are in step and refuses the others. Submits and `exportAll` sync first; what a submit's sync imports stays even if the submit is rejected, and a guard read before the pull then reports E0501. A pull during a submit is caught twice: after acceptance the export is compared again, and a changed file starts the submit over (like a name written by another process), so its sync imports the pull; and no write overwrites a file that changed since the codebase last wrote or read it (unless forced), so a pull in the moment after the commit leaves its file alone and the next operation reports E0513. Queries read the database as it is; `alang db` syncs before each query and, if that fails, answers from the database with the diagnostics on stderr. | Storage, 6.3, 6.7 |

| Moved database | Before each tool call (`card` aside), the server checks that `<dir>/alang.db` is still the file it opened, by device and inode (`Deno.statSync`, recorded at open; where the host has no inode, on Windows, only a missing file counts). | Shutdown | Closing stdin ends the server after the pending answers. | Registration | (2026-11-14, E11.) The server is registered with `--allow-run` beside `--allow-read --allow-write` (README, `scripts/playground-round.sh`), so that acceptance can start the separate process of a program with an `extern fn`; only the server's own code starts processes, and only `deno` without permissions (the CLI had `--allow-run` already). ## Temporary limits

These are not language decisions, only what the implementation does not do yet.

- `if`, `match` and `for` are compiled only as a statement, as the value of `let`, and after `return`.
- `where` on a variant type is rejected (E0225); it is open which name refers to the value.

## Open questions

- **The code of an `extern fn` outside the hash and the history** (E15, 2026-11-14). The database stores the `target` text, so a module edit changes behavior without a new version; every acceptance loads the module afresh and reruns its examples, so the next change of anything reports an example the edit broke. A later rule could store the module's content hash and show its change in `history`.
- **Effects of a pure extern that no permission covers** (E12, 2026-11-14). Acceptance runs foreign code without permissions, so a pure extern that touches files, the network, the environment or processes traps; console output, the clock and randomness need no permission and are not caught. Output could be attributed per example from the separate process.
- **Rejecting a pure function without parameters** (C6, 2026-11-14; E0405 reserved). It is a constant written the long way, so principle 3 wants one form; it stays legal until a round shows whether models still write it, since about 25 test fixtures and stored programs (`tasks.usage`) use it.
- **A constant named in a contract.** Changing a constant's value tightens every `requires`, `ensures` or `where` that names it without a printed interface change (C8); callers with effects have no examples, so they find out at run time. A later rule could make the body of such a constant part of its interface.
- **Exit code 1 means three things.** An `Err` from `main` (its message on stderr), a program the tool refused
  (diagnostics as JSON on stderr), and a JavaScript crash. stderr tells them apart; a distinct code for the tool's
  refusals would make them testable without reading it.
- **Invisible characters in strings (7.2).** `\u{...}` is only for control characters, so a byte order mark,
  `"\u{FEFF}"`, is E0005, and its fix inserts the invisible character itself, which no reader of the text can see
  (the wordcount round, 2026-11-13). Open: write invisible format characters (Unicode category Cf, such as U+FEFF and
  U+200B) only as `\u{...}`, like control characters, so each string keeps one spelling (3).
