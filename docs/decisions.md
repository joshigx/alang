# Design decisions

Gaps in `alang-specs.md` that the implementation had to close. Each is decided by the six principles; the rule
numbers refer to the spec. Open points are listed at the end.

## Lexical

| Topic          | Decision                                                                                                                                                                                                            | Principle                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Comments       | None. `//`, `/*` and `#` get a dedicated diagnostic pointing to `doc`.                                                                                                                                              | 3.7: text is printed from the tree, a free comment would be lost.    |
| String escapes | Exactly `\"`, `\\`, `\n`, `\t`, and `\u{X}` (uppercase hex) for other control characters. Every other character, including non-ASCII, is written as itself; `\u{41}` is rejected. Raw control characters are rejected. | 3: every string has exactly one spelling.                            |
| Strings        | Double quotes only, closed on the same line.                                                                                                                                                                        | 3                                                                    |
| Numbers        | 4.7 is enforced both ways: `65535` and `1_000` are errors, as are leading zeros. Floats are `digits.digits`, never in exponent form; the printer expands `1e-7` to `0.0000001`. `-0` is rejected.                                                                                  | 3, 4.7                                                               |
| Negative       | `-3` is a literal. There is no unary minus on other expressions; write `0 - x`.                                                                                                                                     | 3: one form.                                                         |
| Keywords       | Section names (`doc`, `in`, `out`, `effects`, `requires`, `ensures`, `examples`, `body`, `record`, `variant`, `where`) are reserved, so `out: Unit` can never be read as a parameter.                                | 1: no lookahead needed.                                              |
| Foreign forms  | `===`, `!==`, `&&`, `\|\|`, `!`, `{`, `}`, `[`, `]`, `?`, `;`, `'`, `var`, `null`, `while`, `import`, ... have dedicated diagnostics (E0006).                                                                       | 5.7                                                                  |

## Syntax

| Topic                | Decision                                                                                                                                                                                                         | Principle                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Line breaks          | Required between statements and section entries. Inside `( )` of calls and constructs they are ignored. Indentation never matters.                                                                               | 3.7                                           |
| Parentheses          | Not stored in the tree. The printer emits exactly those that 3.5 requires (and `a - (b - c)` on the right of the same group). `(a) + b` prints as `a + b`.                                                       | 3.7                                           |
| Lambdas as operands  | Always parenthesized, since a lambda body extends as far right as possible: `(fn(x: Int): Int => x) == f`.                                                                                                     | 3.7                                           |
| `not`                | Binds looser than comparison: `not a == b` is `not (a == b)`.                                                                                                                                                    | 3.5                                           |
| `a.b.c`              | Parsed as a neutral dotted name; whether it is a local with fields or a qualified constant is resolved later. A dotted path followed by `(` is a call; if its first segment is a local, it is a method call and reported (E0220). | 3.1, 1.2                                      |
| `f<T>(...)` vs `a < b` | After a path, `<` starts type arguments only if a type list closed by `>` and followed by `(` parses; otherwise it is a comparison.                                                                             | 1.4                                           |
| Variant case names   | A case's full name is `module.Case`, so case names are unique per module across types. Written short inside the module.                                                                                          | 1.2: one name, one meaning.                   |
| `if` without `else`  | Only as a statement; an `if` that yields a value (after `let ... =`, `return`, or inside an expression) needs `else` (E0110).                                                                                   | 3.4                                           |
| Block value          | The value of a block is its last statement if that is an expression, otherwise `Unit`.                                                                                                                           | 3.4                                           |
| Definition names     | Always have a module: `fn main` is rejected, `fn hello.main` is required.                                                                                                                                        | 6.2                                           |

## Semantics and runtime

| Topic                | Decision                                                                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `let ... else`       | In the `else` branch `error` is the `Err` value; for `None` it is `Unit`.                                                                      |
| `result`, `error`    | Bound by the language (in `ensures` and in `let ... else`), so they cannot name a parameter or binding (E0109). Fields may use them.          |
| `std.int.parse`      | `String -> Option<Int>`: optional `-`, decimal digits, inside the `Int` range.                                                                 |
| `Int` division       | `/` truncates toward zero, `%` has the sign of the dividend (`-7 % 2 == -1`), division by zero traps.                                          |
| `Float` arithmetic   | IEEE 754; a NaN result traps (`0.0 / 0.0`), infinities are ordinary values (`1.0 / 0.0`).                                                      |
| String order         | By Unicode scalar values, not UTF-16 code units. `std.string.length` counts scalar values.                                                     |
| Representation in TS | `Int`/`Float` → `number`, `Unit` → `null`, records → plain readonly objects with a checking constructor, variants → `{ tag, value? }`.        |
| Names in TS          | Global paths joined with `$` (`net$port$parse`), so they never collide with locals. Locals that are TS reserved words get a `$` suffix.        |
| Effects in TS        | Leave one trace: a function with effects is `async` and every call to one is awaited (the checker marks these calls). The language stays sequential, since each call ends before the next statement; only the output is asynchronous, because network and waiting exist only asynchronously in JavaScript. Pure functions, lambdas, conditions and examples stay synchronous: pure code cannot call effectful code (2.1, 2.4, 5.4). An over-declared effect makes a function async that never waits, which costs nothing. The entry file awaits `main`. Enforced through Deno permissions on `main`. |

## Type checking

| Topic                   | Decision                                                                                                                                                                                                                                                    | Principle                                  |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Direction               | Types flow forward only. The left operand of `==` is typed first and the right one checked against it, so `parse(...) == Ok(...)` works and `None == x` does not (E0210).                                                                                 | 1.4                                        |
| `Ok`, `Err`, `None`     | Take their type from the expected type only; without one they are an error (E0210). `Some(x)` can also take its type from `x`.                                                                                                                            | 1.4                                        |
| Explicit type arguments | Written exactly when a type parameter of the function does not occur in any parameter type (`std.list.empty<Int>()`); never otherwise (`std.list.map(...)`, E0209). The rule depends on the signature only, so each call has one spelling.               | 1.4, 3                                     |
| Generic calls           | Type parameters are bound from the arguments, left to right, without backtracking.                                                                                                                                                                         | 1.4                                        |
| Arguments               | Every parameter is named, in declaration order, none omitted, none twice (E0205–E0208). Records are built the same way.                                                                                                                                  | 4.1, 2.6                                   |
| Conversion              | None. `Int` never fits `Float`; the fix suggests `1.0` or `std.int.to_float(value: x)`.                                                                                                                                                                  | 2.6                                        |
| `+` on `String`         | Not allowed; texts join with `std.string.concat`. `+` is numeric only, since one name denotes one function.                                                                                                                                              | 2.6                                        |
| Order                   | `< <= > >=` only on `Int`, `Float`, `String`. `==` on every type without function values (E0222).                                                                                                                                                        | 3.9                                        |
| Shadowing               | A binding may not reuse a name that is visible at that point (parameters, outer `let`s, enclosing pattern bindings, lambda parameters). Sibling branches may reuse a name, e.g. `case Circle(v)` and `case Square(v)`.                                     | 2.6                                        |
| Locals vs functions     | A plain name resolves to a local first, then to a function of the module (`by: compare`). A path followed by `(` is always a call.                                                                                                                         | 1.2                                        |
| Own module names        | A name of the definition's own module is written short everywhere: types, calls, function values, constructions, patterns and examples. The full spelling (`net.port.Port` inside `net.port`) is an error with the short form as fix (E0226), reported only for a name that exists, so a misspelled one is just unknown (E0201–E0203). One exception: a function passed as a value whose short name a local holds (`by: m.backwards` with a parameter `backwards`) is written in full, since the short form would mean the local; the full name is then the only spelling, and not reported. One spelling per name keeps one text, and so one hash, per meaning. Enclosing and nested modules are other modules and are written in full. The codebase applies this fix itself (Database, Own-module names). | 1.2, 3.7 |
| Function values         | A function name can be passed as a value (`by: std.int.compare`) if it is not generic; a generic one needs a lambda (E0210).                                                                                                                              | 3                                          |
| Discarded values        | An expression statement whose value is not used must have type `Unit` (E0217); dropping a `Result` silently is an error. A `for` used as a statement has type `Unit`; its body values must be `Unit` too.                                                 | 2.3, 5                                     |
| Function end            | The last statement of a body is literally `return` (E0218). Statements after a `return`, or after an `if`/`match` whose branches all return, are unreachable (E0218).                                                                                     | 3.4                                        |
| Blocks                  | A block's value is its last expression. A block that ends in `return` has the bottom type and fits any expected type. A value block that ends in `let` is an error.                                                                                      | 3.4                                        |
| Lambdas                 | The body is one expression; `return` and `let ... else` inside it are errors (E0219). Lambdas may read enclosing bindings.                                                                                                                                | 2.4                                        |
| `match`                 | Exhaustive over nested patterns (`Err(NotANumber)` + `Err(OutOfRange(n))`). A case covered by earlier cases is an error (E0214). A case with a value is always written with a sub-pattern, a case without one never. `match` on `Int`/`String` cannot be exhaustive. A name where an earlier case of the same `match` names a specific case at that position (`case Err(std.fs.NotFound)`, then `case Err(other)`) stands for the remaining cases, a catch-all, and is rejected (E0227, chosen by the user 2026-11-12 after the spec's blind test): a case added later would not be reported there. Also for `Option`, `Result` and `Order`, since 3.3 has no catch-all at all. A name first makes the later specific case unreachable (E0214) instead. | 3.3                                        |
| Examples                | The left side calls the function the example belongs to (E0221); both sides have the same type.                                                                                                                                                           | 5                                          |
| Scopes of conditions    | `requires` sees the parameters, `ensures` the parameters and `result`, `where` the fields, examples nothing.                                                                                                                                              | 5                                          |
| Uniqueness              | Definitions, parameters, fields, and case names per module are unique; a case may not share its name with a type of the module (E0215).                                                                                                                  | 1.2                                        |
| Reserved names          | Types and cases may not be named like builtins (`Option`, `Ok`, `Unit`, ...), since those are always written short. The module `std` is reserved for the standard library (E0215).                                                                       | 1.2                                        |
| Diagnostics             | All causes are reported, one diagnostic each. An expression that failed has an error type that fits everywhere, which suppresses follow-ups; a broken pattern suppresses the exhaustiveness check of its `match` (5.6). Unknown names get a "did you mean" fix within a small edit distance. | 5.5, 5.6                                   |
| std signatures          | Kept in `src/std.ts` with function types and type variables, which the surface language cannot express yet. A test keeps them in sync with `runtime.ts`.                                                                                                  | —                                          |

## Effects

| Topic                  | Decision                                                                                                                                                                                                                                   | Principle |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------- |
| Spelling               | Effects are listed once each, in the order of the effect table (`effects: fs.read, console`); anything else is a parse error with the reordered line as fix (E0111).                                                                     | 3         |
| Calls                  | A function declares every effect of every function it calls; checking direct calls is enough, since each callee's list is checked in turn (E0230). One diagnostic per definition, at the first offending call, with the complete corrected `effects:` line as fix. | 2.1, 5.6  |
| Over-declaration       | Allowed. 2.1 asks that the caller's effects *include* the callee's. Requiring an exact list would make removing the last effectful call a signature change that ripples up to `main`, against "signature unchanged, callers follow" (6). | 2.1, 6    |
| Lambdas                | Pure: a call with effects inside a lambda is an error (E0232). Effects per element go through `for`.                                                                                                                                      | 2.4       |
| Function values        | A function passed by name (`by: compare`) must have `effects: none`, like a lambda, since function types carry no effects (E0232). One exception: a std parameter marked as taking a function with effects (the `handler` of `std.http.serve`, shown as `... with effects`) accepts a named function with effects, and passing it counts like calling it: the caller declares its effects (E0230). Inside a lambda or a condition it is still E0232 or E0233; a lambda passed there is still pure. User code cannot declare such a parameter, since it has no function types. | 2.1, 2.4  |
| Conditions, examples   | `requires`, `ensures`, `where` and examples call only pure functions (E0233). An example of a function with effects is therefore an error: it would run the effects at every acceptance.                                                 | 5.4       |
| Runtime                | `alang run` starts `main` in its own Deno process with `--no-prompt` and exactly the permissions of its effects (`fs.read` → `--allow-read`, ...). A refused operation traps (`effect`); it is not an ordinary error value.              | 2.5       |
| `std.fs.read_text`     | `String -> Result<String, std.fs.Error>` with cases `NotFound`, `PermissionDenied` (by the OS), `IsADirectory`, `Other: String`; the error type is shared by every `std.fs` function (Files, arguments and console). std types are written in alang (`STD_TYPES_SOURCE` in `src/std.ts`). | 2.3       |
| Diagnostics            | An unknown name, type or function is reported once per definition, however often it is used (5.6).                                                                                                                                       | 5.6       |

## HTTP server (`std.http`)

| Topic             | Decision | Principle |
| ----------------- | -------- | --------- |
| `serve`           | `std.http.serve(host: String, port: Int, handler: (std.http.Request) -> std.http.Response with effects): Result<Unit, std.http.ServeError>`, effects `net`. It returns only when serving ends: `Ok(Unit)` after SIGINT or SIGTERM, `Err` if it cannot listen. Code after it runs after the server stopped. | 2.3, 3.4 |
| Host              | A parameter, not a default: whether a server is reachable from other machines (`"0.0.0.0"`) or only this one (`"localhost"`) is visible at the call. | 2.6 |
| One at a time     | Requests are answered in the order they arrive; a handler never starts before the previous one returned. alang has no concurrency, and a handler with effects (a file it writes) must not interleave with itself. Reading a request's content happens before its turn. | Overview |
| Handler           | A named function with effects, or a pure one (by name or as a lambda). The recommended form is a pure function with examples for the logic and a thin handler for the effects (`examples/server.alang`). | 5.1, 2.4 |
| Records           | `Request(method, path, query, headers, content)`, `Response(status, headers, content)`, `Header(name, value)`. The field is `content`, since `body` is a reserved section name. All values are `String`/`Int`: method in capitals as sent, path and query as sent (query without `?`), content as UTF-8 text. | 1, 3 |
| Request headers   | Names in lowercase, sorted by name, repeated headers joined with `, ` (as fetch does). One list form on every host, so examples can state it. | 3 |
| `Response` where  | `200 <= status and status <= 599 and (content == "" or (status != 204 and status != 205 and status != 304))`: what fetch accepts, checked at construction like any record (a `where` trap), so examples catch it at acceptance. | 5 |
| Response headers  | Without a `content-type` header, non-empty content is sent as `text/plain; charset=utf-8`; empty content is no body and gets no content type. A header name that is not an HTTP token, or a value with a line break or a character above U+00FF, traps (kind `http`), checked by the runtime so that both hosts behave alike. | 3, 5.3 |
| Errors            | A taken port is `AddressInUse`, an OS refusal (port below 1024) `PermissionDenied`, anything else (invalid port, unknown host) `Other` with the host's message: the environment, not the program, is at fault (2.3). A missing `--allow-net` traps (`effect`), as for `std.fs.read_text`. | 2.3, 2.5 |
| Traps             | A trap in the handler, or in sending its response, ends the program as everywhere: that request gets status 500 without content, later requests are not handled, and the trap reaches the entry from where `serve` was called (exit 70, diagnostic on stderr). A request the runtime cannot read (a target that is no path, a client that disconnects while sending) gets 400 and is not a trap: nothing a client sends ends the server, only what the program does. | 5.3 |
| Signals           | `serve` listens to SIGINT and SIGTERM only while serving. The first one stops accepting and answers the requests in progress; a second one ends the program at once, since the listeners are gone and Deno and Node.js both restore the default action (checked). Nothing is printed on listening; the program decides its output. | 2.6 |
| `alang run`       | Waits for the program on SIGINT (a terminal's Ctrl-C reaches the program itself, which may end on its own terms) and passes SIGTERM on to it. Both `alang run` and `alang db run`. The price: a SIGINT sent to the tool's process alone (`kill -INT`) is ignored and the program keeps running; passing it on would deliver a terminal's Ctrl-C twice, and the second one ends a server at once. | — |

## Files, arguments and console

| Topic | Decision | Principle |
| --- | --- | --- |
| Error type | One variant type, `std.fs.Error` (renamed from `ReadError`; the user's choice D2, 2026-11-13), for every `std.fs` function, with the cases `NotFound`, `PermissionDenied`, `IsADirectory` and `Other: String`. A second error type in `std.fs` could not reuse these names: a case's full name is `module.Case`, and `DefChecker.declare()` in `src/check.ts` (pass 2 of `checkProgram`, which declares `STD_TYPES` like user types) reports a case name repeated in a module as E0215 ("Case `X` already exists in module `M`; case names are unique per module"). The list is final once published (3.8): E0227 forbids a catch-all, so an added case would break every `match`. Each case is a promise that every host classifies alike, so not-a-directory, already-exists, not-empty and disk-full go to `Other`, whose host message differs between runtimes: shown, not compared. | 3.3, 3.8, 2.3 |

## Examples and acceptance

| Topic                | Decision                                                                                                                                                                                                                                                      | Principle |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| Acceptance           | One pipeline (6.3): parse, type and effect check, mandatory examples, then run the examples. `alang check`, `ts`, `build` and `run` go through it and refuse a program that fails any step; `fmt` and `test` do not.                                          | 5, 6.3    |
| Missing examples     | A function with `effects: none` and `examples: none` is rejected (E0401), located at `examples: none`. `expected` shows the form of an example from the signature (`twice(n: Int) == Int`); there is no fix, since no tool can invent the expected value.     | 5.1, 5.5  |
| Same round           | E0401 is static and reported together with type and effect errors. Examples run only when there are none of these, since they need the generated code.                                                                                                        | 5.6       |
| Failing example      | Rejected with E0402. The message quotes the call and its actual value as alang text. There is no fix: whether the body or the example is wrong is the author's call, and replacing the expected value by the actual one would write the bug into the example. | 5.1, 5.5  |
| Trapping example     | Rejected with E0403, naming the trap kind (`requires`, `where`, `overflow`, ...) and its message. A trap on the expected side (`Ok(Port(value: 0))`) counts the same.                                                                                         | 5.3       |
| Runaway recursion    | A stack overflow while running an example is a trap of kind `stack` (E0403), not a crash of the tool. Recursion is the only way to repeat (3), so a missing base case is a common mistake.                                                                    | 3, 5      |
| Every failure counts | All failing examples are reported, one diagnostic each. Several failures of one function give the author more evidence about what is wrong.                                                                                                                   | 5.6       |
| Equality             | An example holds if both sides are equal under `==`, i.e. structurally (3.9). The left side runs first.                                                                                                                                                       | 3.9       |
| Actual values        | Printed from the static type of the call, as canonical alang written from the function's module (`net.port.Port(value: 80)` outside `net.port`), so they can be pasted into an example. Lists print as `std.list.append` chains; infinities as `1.0 / 0.0`.   | 1.2, 3.7  |
| Where examples run   | In the tool's process, on the generated TypeScript (spec, Toolchain).                                                                                                                                                                                         | —         |

## Database

| Topic | Decision | Principle |
| --- | --- | --- |
| Hash | sha-256 of the canonical text (the printer's output, never the submitted text), hex, first 16 characters. Storing a version whose hash exists with a different text is an internal error (collision). The same text always gets the same hash, so a revert, or a remove followed by an add, reuses the earlier version. | 3.7, 6.1 |
| References stay names | **Departs from 6.1.** Stored text refers to other definitions by name, as written; there is no internal hash link. The `text` column holds canonical text and rows never change, and that text contains the definition's own name, so no design that stores it can make `rename` change only a pointer. The guard (6.7) needs a hash that changes exactly when the text a query returned changes; with hash links, a callee's change would re-hash every transitive caller and stale their guards although their text did not change. Consequence: `rename` rewrites every caller, and each caller gets a new version (built later). Recorded alternative: hash-linked storage as in Unison, which needs cycles hashed jointly and stored text that is not the canonical text. | 6.1, 6.7 |
| Tables | As in the spec, except: `names.hash` is unique (a text contains its name, so one version belongs to one name); `refs(from_hash, to_name)` holds names, not hashes, so that `callers(B)` still lists A after only B's body was replaced; `history(id, name, hash, changed_at, operation, other_name)` with `hash` null for a removal and `id` giving the order (one transaction shares a timestamp). `refs` and `signature` are derived from the text. | 6.1, 6.6 |
| `refs` rows | Every full name a version refers to, in order of first use (std names and the definition itself included). A variant case is stored by its own full name (`net.port.OutOfRange`), not its type's, so the rows depend on the text alone and never go stale; `callers` of a type also looks up the users of its cases. | 6.5 |
| Transactions | `submit(changes)`, a change being `add(text)`, `replace(name, hash, text)`, `remove(name, hash)` or `rename(name, hash, to)`, optionally with a text (Rename checks). Each text is parsed on its own and is exactly one definition (E0504); a replaced text keeps the name (E0505; the name also fixes the kind); a name is changed at most once per transaction (E0508). The whole resulting program is then accepted (6.3), which re-runs every example, so a caller whose example a changed body breaks is reported. Either everything is written, in one SQLite transaction, or nothing. | 6.3, 6.4 |
| Guard | `replace` and `remove` with a hash that is not current are rejected (E0501) with the current version in the result's `current` and a fix to the current hash. `add` of an existing name is rejected (E0503), also with the current version. An unknown name (E0502) gets a closest-name fix. Diagnostics of database operations quote the operation as `at`, e.g. `replace(net.port.parse, 1a2b...)`. | 6.7, 5.5 |
| Interface rule | "If `replace` changes the signature, it is rejected and names the affected callers" leaves out the two sections that concern only the definition itself: `doc` and `examples`, so adding an example does not force every caller into the transaction. Everything else counts: for a fn `in` (names, types, order), `out`, `requires`, `ensures` and added effects; for a type its shape (record or variant, fields, cases with payloads, in order) and `where`. Contracts count although acceptance re-runs every example, because callers with effects have no examples (5.4): a tightened `requires` would otherwise surface only as a trap at runtime. Contracts are compared as printed (no proof of implication yet, 5.2); types by full name. The baseline is the current version as the transaction's renames rewrite it, so adapting a definition to a type renamed in the same transaction is no interface change. A change with callers outside the transaction is rejected (E0506), listing them; submitting them unchanged in the same transaction is enough. | 6, 6.4, 5.4 |
| Added effects | Removing an effect is compatible, since over-declared effects are allowed (Effects). An added effect lists every caller that would have to declare it, transitively: the walk stops at callers that declare it already and at members of the transaction. One round shows the whole chain, instead of one layer per attempt. | 2.1, 5.6 |
| Remove | Rejected while callers outside the transaction exist (E0507). Recursion and a function's own examples do not count, nor callers removed in the same transaction. Removing the last definition leaves an empty, accepted program. | 6 |
| Rename | `rename(name, hash, to)` rewrites the renamed definition under its new name and every definition that refers to it (followers), written from its own module: short inside, qualified elsewhere. All renames of a transaction go through one mapping; a variant type that changes module takes its cases along (`net.port.NotANumber` becomes `net.errors.NotANumber`), since case names belong to the module. A caller whose text does not change is not rewritten. History: the new name gets `rename` (other name: the old one), the old name a `rename` entry without hash, each follower `follow`; `history` of the new name continues with the old name's entries. | 6.1 (departs), 1.2 |
| Rename checks | The new name must be free (E0503), differ from the old one, lie outside `std`, and survive printing and parsing as a name of the definition's kind (E0509); both names count toward "one change per name" (E0508). To rename and edit a definition in one transaction, `rename` takes an optional text, `rename(name, hash, to, text)`: the changed definition under its new name (E0505 otherwise), guarded by the one hash. It is written, not rewritten: it counts as a member of the transaction for the interface and remove rules, its own references are not compared for capture (E0510), and its interface is compared with its mechanically renamed form, so callers that the text's interface change affects join the transaction as with `replace`. Followers and renamed definitions are outside the transaction for the interface and remove rules, since they are rewritten, not adapted; a `replace` of a follower in the same transaction wins over the rewrite. | 6.4, 6.7 |
| Rename capture | A rename must not change what a reference denotes. A new name can be captured by a local binding: a function value `by: cmp` renamed to `g` reads a local `g`, and a module renamed to `path` turns `path.parse(...)` into a method call on a parameter `path`. Before acceptance, the program is checked and each rewritten definition's references are compared with its old ones mapped through the rename; a difference, or a diagnostic inside a rewritten definition, is reported as E0510 instead of the type errors that follow from it. | 1.2, 5.6 |
| Command line | `alang db [--dir <dir>] <command>`: every query and operation, one JSON value on stdout (all but `run`, below), exit code 1 for a rejected operation (diagnostics in the result) or an unknown name (diagnostics on stderr). `submit <file>` takes a JSON array of changes, so a transaction of several changes (6.4) is possible from the shell. Texts come from files or stdin (`-`). | 6, 5.5 |
| Run | `alang db [--dir <dir>] run [<main>]` (`Codebase.run`) syncs, accepts the whole current program (6.3), writes it to `out/<main>.ts` with its entry `out/<main>.run.ts` (both stay and are overwritten by the next run, like those of `alang run`), and starts `main` in its own process with exactly the permissions of its effects. Acceptance re-runs every example although every stored state was accepted, so `db run` and `alang run` share one pipeline and a checker newer than the database is noticed. A codebase of many modules can hold several `main` functions: the full name chooses one, and without it there must be exactly one (E0304, listing them). An unknown name is E0502 with a closest-name fix; a definition not named `main` is E0304, since a program starts at a function named `main` (1). A failed sync refuses the run instead of falling back to the database as queries do: an export file that does not parse or check is what the user meant to run, and with E0513 the files contradict the database; either way a run has effects. Stdout belongs to the program; diagnostics go to stderr as JSON with exit code 1; otherwise the program's exit code is passed through (70 for a trap). The program runs in the caller's directory, not the codebase's, like `alang run`. | Toolchain, 6.3 |
| Own-module names | Chosen by the user (2026-11-12) after the playground. Submit and import store an own-module name written in full short instead of rejecting it (E0226), since the stored text, and so the hash, is the same either way: like layout, the full spelling does not survive printing. Applied in the syntax tree, to exactly the places the checker reported, and only when every diagnostic of the program's check is such a name in a definition sent with the change; with any other complaint everything is reported as before, so each diagnostic quotes the text as sent (5.5). The shortened program is checked again; if that fails, the E0226 are reported. A successful result lists the applied diagnostics under `fixed` (absent when empty), so the caller knows where the stored text differs from its own. A rejection after shortening (an example, an interface change) lists them first, since its quotes are of the short text. Shortening comes before the interface rule, so a contract that names its module in full is no change. `alang check` on a file still reports E0226. Other mechanical fixes (effect order E0111, type arguments E0209) are still rejected. | 1.2, 3.7, 5.5 |
| No-op replace | A replace whose canonical text equals the current one is accepted and writes nothing; the result lists it under `unchanged`, not `written`. | 6.6 |
| Concurrency | Submits of one codebase run one at a time. The write runs in `BEGIN IMMEDIATE` and first compares all names with the snapshot that was accepted; if another connection wrote in between, the submit starts over (up to three times), so its guards report what changed (tested with a second connection). Each open codebase accepts into its own file (`out/accept-<pid>-<n>.ts`), so two processes never run each other's program. The file exists only while an acceptance runs and is removed right after it, since the module is loaded by then: a process killed between acceptances (MCP clients end their servers with a signal, which skipped the removal on close) leaves nothing behind. | 6.3 |
| Queries | Every query returns the hash of each definition it read (std entries have none). An unknown name throws E0502 with a closest-name fix, located at the query (`context(net.port.pars)`). | 6.7, 5.5 |
| std in queries | `definition`, `signature`, `context`, `callers` and `list` answer for std names too, with hash null, since a model writing a call needs the fields of `std.http.Request` as much as those of its own types (the playground model read `src/std.ts` instead). A std type is its alang text; a std function its signature on one line (`signatureLine`), since it has no alang body and some of its types no surface syntax; `signature` gives the same. `context` of a std name lists the types its signature mentions, a function parameter's included (`serve`'s handler: `Request`, `Response`), then the types in theirs. `history`, `replace`, `remove` and `rename` of a std name are E0502 with a message saying it is the read-only standard library, not that it does not exist. Closest-name fixes consider std names and modules. | 6.5, 5.5 |
| `signature` | Every section except `body`; for a type, its whole text. | 6 |
| `context` | The text, then what it uses in order of first use: functions and types as their signature, the type of each case used, std functions as one line (`fn std.fs.read_text(path: String): Result<String, std.fs.Error>, effects: fs.read, doc: "..."`, not alang syntax, since std has type parameters and function types), std types as alang text. Then the types in those signatures, one level deep: calling a function means building its arguments. The definition itself is not among its uses. | 6.5, 2 |
| `list` | The definitions whose module is exactly the given one (name, hash, kind, doc) and the names of its direct submodules; `list("")` gives the top-level modules, also on an empty codebase. `list("std")` and its submodules list the standard library (hash null); `std` is not among the top-level modules, so an overview of the codebase does not present the library as the user's code; the tool descriptions name it instead. Any other unknown module is E0502. | 6.2 |
| `search(text)` | Case-insensitive substring match in full names and `doc`, std included, sorted by name. | 6 |
| `search(type)` | Pattern `T1, T2 -> R`, `-> R` without parameters; a malformed pattern is E0511 with the expected form. `_` matches any type; a one-segment name matches by last segment (`Port`), a qualified one exactly. A std type variable matches any type but the same one at each occurrence; a function-typed std parameter matches only `_`. Parameters match by position, not name. Each hit comes with a one-line signature. | 6 |
| `history` | Every version, oldest first, removals included (hash null), with the current hash or null if removed. A name that came from a rename continues with the old name's entries before the rename. A name that never existed is E0502. | 6.6 |
| Export | `export/<module>.alang`, one file per module, its definitions sorted by name, as stored canonical text separated by one empty line. After each committed transaction the files of the affected modules are rewritten (via a temporary file and a rename); a module without definitions loses its file. `exportAll` first syncs (below), so it never overwrites files that Git changed, then rewrites everything and deletes stale files; `exportAll({ force })` (`alang db export --force`) skips the sync and lets the database win. A rejected transaction touches no file. | Storage, 3.7 |
| Import | The export is the recommended source of truth, so `importAll` rebuilds the current names from `export/*.alang` (or another directory): the whole program is accepted first, then names whose version differs get it, and names missing from the export are removed, both with history operation `import`. Existing history stays (6.6). A definition in a file other than its module's is rejected (E0512). The derived columns are recomputed where they differ, so importing the same export twice changes nothing. Import does not write the export; it records what the files held (below). A parse error names its file in the message, since it names no definition. | Storage, 6.6 |
| Sync | The export in Git is the source of truth, so the database follows it without a manual step. Table `export_files` holds per module the hash of what its file held when the codebase last wrote or read it (R). `sync` compares, per module, the file (F), what the database would write (D) and R: F = D is in step; F = R ≠ D means the database is ahead (an export write failed after a commit), so the file is written; D = R ≠ F means the file changed (pull, checkout, edit), so the export is imported; all three different is refused (E0513, at `export/<module>.alang`, pointing to `import`, which keeps the database's versions in history, or `export --force`). Files the database is ahead on are written before the import; files left non-canonical by it are rewritten after, so a sync ends with every file as the database would write it. A missing export directory has not been written yet; it is not read as every file deleted. A database without records (from before them) records the files that are in step and refuses the others. Submits and `exportAll` sync first; what a submit's sync imports stays even if the submit is rejected, and a guard read before the pull then reports E0501. A pull during a submit is caught twice: after acceptance the export is compared again, and a changed file starts the submit over (like a name written by another process), so its sync imports the pull; and no write overwrites a file that changed since the codebase last wrote or read it (unless forced), so a pull in the moment after the commit leaves its file alone and the next operation reports E0513. Queries read the database as it is; `alang db` syncs before each query and, if that fails, answers from the database with the diagnostics on stderr. | Storage, 6.3, 6.7 |

## MCP server

| Topic | Decision | Principle |
| --- | --- | --- |
| Scope | `alang mcp [--dir <dir>]` offers the eight queries and the four operations of section 6 as tools (`search_type` for `search(type)`), plus `submit` for a transaction of several changes (6.4) and an optional `text` on `rename`. `import` and `export` stay on the command line: they resolve E0513, and which side wins is the user's call. Only tools, no resources or prompts. | 6, 6.4 |
| No SDK | The protocol is written by hand (`src/mcp.ts`, about 200 lines for transport and dispatch), like `tests/assert.ts`: the project downloads nothing. A tools-only stdio server needs `initialize`, `server/discover`, `ping`, `tools/list` and `tools/call`. | — |
| Protocol eras | Both are served. A request whose `_meta` names a version (`io.modelcontextprotocol/protocolVersion`) is of the stateless era (2026-07-28): it gets `resultType`, server info in `_meta`, and `ttlMs`/`cacheScope` on `tools/list`; an unsupported version there is error -32022 listing the supported ones. Any other request follows the `initialize` era (2024-11-05 to 2025-11-25): `initialize` echoes a version it knows and otherwise offers 2025-11-25. The server does not insist on `initialize` coming first. A line holding an array is a batch (2025-03-26 only, accepted from every client) and gets an array of the responses. | — |
| Results | Each tool answers with one text block holding the JSON value that `alang db` prints for the same command, so the two front ends never differ. Diagnostics (an unknown name, a rejected transaction) and arguments that do not fit are tool results with `isError: true`, since a model can act on them; JSON-RPC errors are only for malformed messages, unknown methods and unknown tools. Unknown arguments are rejected, not ignored: `list` with `name` instead of `module` would otherwise list the top level. | 5.5 |
| Sync | Every query syncs first (`Codebase.sync`), as `alang db` does; a submit syncs by itself. If the sync fails, the query answers from the database and a second text block carries the sync's diagnostics: the model sees no stderr. | Storage |
| Order | Tool calls run one at a time, in the order received; `ping` and the other requests are answered at once. | 6.3 |
| Stdout | Holds protocol messages only. The server sends `console.log` to stderr, so nothing printed in the process (a generated program calling `std.console.print_line`) can break the stream. | — |
| Annotations | Queries are marked `readOnlyHint`, operations not; `add` is the only operation not marked destructive. Caveat: a query syncs first, so it can change the database when Git changed the export (a deleted file removes its module). The hint describes what the model asks for, not what the sync does; a client that runs read-only tools without asking would run that sync unprompted. | Storage |
| Instructions | The server's `instructions` start with the absolute path of `alang-specs.md` next to the sources (when they run from files), so a model that can read files finds the language without a project `CLAUDE.md` (kept by the user, 2026-11-12, although it means reading the whole spec up front); a resource would serve models without file access, against tools only (Scope). They describe the path of a change (find, `context`, `replace` with the hash), that std is found and read with the same tools, rule 1.2 (own module short, others in full), the result shapes including `fixed`, what to do on E0501 and E0506, and that E0513 is reported to the user instead of resolved. | Storage |
| Shutdown | Closing stdin ends the server after the pending answers. SIGINT, SIGTERM and SIGHUP close the codebase and exit with 0, abandoning a call in progress (nothing is written before its transaction commits); clients end servers this way (every playground session left an acceptance file before). | — |

## Temporary limits

These are not language decisions, only what the implementation does not do yet.

- `if`, `match` and `for` are compiled only as a statement, as the value of `let`, and after `return`.
- `where` on a variant type is rejected (E0225); it is open which name refers to the value.
- `const` and `extern fn` are not parsed yet.
- Maps have no alang form for actual values (std has no constructor); they fall back to `std.text.show`.

## Open questions

- **List literals.** The grammar has none, so examples cannot easily mention a non-empty list. Options: a literal form
  `List(1, 2, 3)`, or library functions only.
- **Function types.** `std.list.sort(list, by: compare)` needs a type for a function parameter; the grammar has no
  syntax for it.
- **Form of `const` and `extern fn`.**
- **`std.text.show` of records.** Records carry no type name at runtime, so they show as `(value: 8080)`, not
  `Port(value: 8080)`.
